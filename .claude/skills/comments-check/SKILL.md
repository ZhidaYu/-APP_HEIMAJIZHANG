# 代码注释检查

当用户调用此技能时，对项目代码进行三项注释检查：

1. **注释量检查**：是否有足够的注释（目标：约 30% 注释率）
2. **注释准确性检查**：注释内容是否和代码实际行为一致
3. **注释可读性检查**：注释是否从技术小白视角编写，通俗易懂

---

## 执行步骤

### 步骤 1：确定检查范围

询问用户要检查哪些文件。如果用户没有指定，默认检查 `src/` 下所有 `.ts` 和 `.tsx` 文件（排除类型定义文件 `types.ts`，因为纯类型定义不需要注释密度）。

## 检查维度一：注释量（占比 40%）

### 检查规则

对每个函数（或 10 行以上的代码块），计算注释行数占比：

```
注释率 = 注释行数 ÷ 总行数 × 100%
```

### 评分标准

| 注释率 | 得分 | 说明 |
|--------|------|------|
| ≥ 30% | 10 分 | 优秀，差不多每 10 行有 3 行注释 |
| 20% ~ 29% | 7 分 | 良好，大部分关键代码有注释 |
| 10% ~ 19% | 4 分 | 不足，很多代码缺少注释 |
| < 10% | 1 分 | 严重欠缺，几乎没有注释 |

### 需要注释的位置

- ✅ **每个函数**：必须有注释说明"这个函数做什么"、"参数是什么"、"返回什么"
- ✅ **核心逻辑**：复杂算法、条件判断、数据转换，每段都要有解释
- ✅ **特殊处理**：边界情况、错误处理、临时方案，必须注释为什么这样做
- ✅ **数据结构**：接口、类型的关键字段要有注释

### 不需要注释的情况

- ❌ 极其简单的代码（如 `const x = 1`、`return true`）
- ❌ 纯类型定义文件（`interface`、`type` 定义本身不求注释率）

### 检查输出

列出每个文件中**缺少注释**的函数或代码块：

```
文件: src/main/database.ts
├── 函数 addExpense (第77行): 缺少函数说明注释 ❌
├── 函数 rowToRecord (第220行): 缺少返回值说明 ⚠️
└── 整体注释率: 22% → 得分 7 分
```

---

## 检查维度二：注释准确性（占比 35%）

### 检查规则

逐条对比注释描述和代码实际行为，看两者是否一致。

**重点检查**：
- 注释说"返回 X"，代码是否真的返回 X？
- 注释说"计算 A"，代码是否在做 A 而不是 B？
- 参数注释的名称和类型，和实际参数是否一致？
- 注释提到的边界情况（如"不为空"），代码是否真的处理了？

### 评分标准

| 准确率 | 得分 | 说明 |
|--------|------|------|
| 100%（完全一致） | 10 分 | 所有注释和代码行为匹配 |
| 有 1 处不一致 | 7 分 | 大部分准确，个别需要修正 |
| 有 2~3 处不一致 | 4 分 | 存在明显误导性注释 |
| > 3 处不一致 | 1 分 | 注释严重错误，必须重写 |

### 检查输出

列出**注释和代码不匹配**的地方：

```
文件: src/shared/categories.ts
├── 第233行 getCategoryDisplay 函数注释:
│   注释写"先查预设分类，没有则返回未知分类"
│   但代码实际还查了 userCategories → 注释遗漏了用户分类的查找逻辑 ❌
│   建议改为: "先在预设分类中查找，若未找到则在用户自定义分类中查找，均未找到返回'未知分类'"
```

---

## 检查维度三：注释可读性（占比 25%）

### 检查规则

以**完全不懂编程的人**的视角阅读注释，判断是否：
- 不用编程术语，或术语有解释
- 一句话能看懂在干什么
- 使用中文（本项目强制要求）
- 没有"显而易见"的无意义注释（如 `// 循环遍历数组`）

### 评分标准

| 可读性 | 得分 | 说明 |
|--------|------|------|
| 技术小白能看懂 90%+ | 10 分 | 术语少、类比重、语言平实 |
| 能看懂 70%~89% | 7 分 | 部分术语需要解释 |
| 能看懂 50%~69% | 4 分 | 很多术语没有解释 |
| 看不懂 | 1 分 | 注释本身就是天书 |

### 常见问题

| 问题类型 | 不好 ❌ | 好 ✅ |
|---------|---------|------|
| 用术语不解释 | `// 递归遍历 AST 节点` | `// 逐层深入检查语法树中的每个元素（递归）` |
| 无意义注释 | `// i 自增` | 这种简单代码不需要注释 |
| 英文注释 | `// Get user data` | `// 从数据库读取用户信息` |
| 太简略 | `// 处理数据` | `// 把传入的日期字符串转换成标准格式（YYYY-MM-DD）` |
| 过于技术化 | `// Promise.all 并发请求` | `// 同时发起多个网络请求，全部返回后再继续处理` |

### 检查输出

列出**小白看不懂**的注释：

```
文件: src/main/database.ts
├── 第16行: "设置 WAL 模式" → 什么是 WAL？建议加一句解释
│   建议改为: "将 SQLite 设置为 WAL 模式（一种写入时不影响读取的机制，提升性能）"
├── 第37行: "迁移：如果没有 type 列，添加它" → 什么是"迁移"？
│   建议改为: "兼容旧版本数据库：检查是否有'收入/支出类型'这一列，没有就补上"
```

## 重要补充

### 注释的原则

**生活类比**：好的代码注释就像 IKEA 家具的安装说明书——不是只写"把木板拼起来"，而是用简单的话 + 图示，让完全没拼过家具的人也能组装成功。

**三个标准**：
1. 在**哪里**需要注释？→ 每个函数、每段复杂逻辑
2. 注释写**什么**？→ 写代码的意图和逻辑，不是翻译代码本身
3. 谁来**读**注释？→ 技术小白，不是程序员同事

### 好注释 vs 坏注释

```typescript
// ❌ 坏注释：翻译代码本身
// 循环 i 从 0 到 n
for (let i = 0; i < n; i++) { ... }

// ✅ 好注释：解释意图
// 逐条检查用户是否有权限访问该分类（只有自己创建的分类才能修改）
for (let i = 0; i < n; i++) { ... }
```

### 检查频率

- 建议在每次提交代码前运行一次
- 或者新增/修改函数后针对性检查

## 常见问题

### Q1: 为什么要求 30% 的注释率？

这是本项目对初学者的友好标准。专业公司可能要求更低（10%~20%），但我们是教学级项目，注释要足够多。

### Q2: 所有代码都要 30% 注释率吗？

不是。纯类型定义（interface/type）、简单的 getter/setter、一目了然的常量定义，不要求注释密度。

### Q3: 注释写太多会不会影响性能？

不会。TypeScript 编译时注释会被自动删除，不影响最终运行的文件大小和速度。
