# 代码安全审计

当用户调用此技能时，对项目代码进行全面的安全检查。

---

## 执行步骤

### 步骤 1：确定审查范围

默认检查以下内容：
- `src/` 下所有 `.ts`、`.tsx`、`.js` 源代码文件
- `package.json`（依赖安全）
- 项目配置文件（`electron-builder.yml`、`.env` 等）
- `.claude/settings*.json`（权限配置）

### 步骤 2：逐项检查

按以下 6 个类别依次检查，每项给出"安全 / ⚠️ 警告 / 🔴 危险"评级。

---

## 检查类别一：敏感信息泄露（硬编码密码/密钥）

### 检查什么

扫描所有代码和配置文件，查找硬编码的：
- 密码（`password`, `passwd`, `pwd`）
- API 密钥（`api_key`, `apikey`, `secret`, `token`）
- 数据库密码
- 加密密钥、盐值（`salt`）

### 搜索方法

```bash
grep -rn -i "password\|passwd\|secret\|api[_-]?key\|token\|private[_-]?key" src/ --include="*.ts" --include="*.tsx"
```

### 判定标准

| 发现 | 评级 | 说明 |
|------|------|------|
| 无任何敏感信息 | 🟢 安全 | — |
| 存在测试用的假数据（如 `password: 'test123'`） | 🟡 警告 | 测试代码也需要避免，容易误提交 |
| 存在真实的密码/密钥 | 🔴 危险 | 必须立即删除，改用环境变量或配置文件 |

---

## 检查类别二：SQL 注入漏洞

### 检查什么

检查所有数据库操作代码，看 SQL 语句是否拼接了用户输入。

### 搜索方法

```bash
grep -rn "prepare\|exec\|\.run\|\.get\|\.all" src/ --include="*.ts"
```

### 判定标准

| 写法 | 评级 | 说明 |
|------|------|------|
| 全部使用参数化查询（`@param` 或 `?` 占位符） | 🟢 安全 | 用户输入作为参数绑定，不会拼接进 SQL |
| SQL 字符串中包含变量拼接（如 `` `SELECT * FROM ${table}` ``） | 🔴 危险 | 攻击者可能通过输入控制 SQL 逻辑 |
| 列名/表名来自硬编码常量（非用户输入） | 🟢 安全 | 即使是拼接也是安全的 |

### 本项目关键检查点

- `src/main/database.ts`：所有 SQL 操作是否使用参数化查询
- 特别注意 `updateExpense` 中的动态 SET 子句拼接——列名虽来自硬编码判断，但需确认
- CSV 导入模块中的数据写入是否走安全的参数化通道

---

## 检查类别三：配置文件敏感信息

### 检查什么

检查所有配置文件中是否有明文敏感信息：

#### package.json
- 是否有私有仓库地址（含凭据）
- 是否暴露了内部服务器地址

#### electron-builder.yml（如果存在）
- 签名证书路径/密码是否硬编码

#### .env / .env.local / .env.production
- 所有 `KEY=value` 条目是否为敏感信息

#### .claude/settings*.json
- 权限白名单是否过于宽松
- 是否有危险的 Bash 权限（如 `rm -rf /`）

### 判定标准

| 发现 | 评级 | 说明 |
|------|------|------|
| 无敏感配置 | 🟢 安全 | — |
| 权限配置过于宽松 | 🟡 警告 | 如 `Bash(*)` 表示任何命令都能跑 |
| 包含密钥/密码 | 🔴 危险 | 必须移到环境变量 |

## 检查类别四：Electron 安全（本项目专用）

### 检查什么

Electron 桌面应用有独特的安全风险：

#### ① webPreferences 配置（`src/main/index.ts`）

检查创建 `BrowserWindow` 时的安全设置：

| 配置项 | 安全值 | 说明 |
|--------|--------|------|
| `nodeIntegration` | `false` | 禁止渲染进程直接访问 Node.js |
| `contextIsolation` | `true` | 隔离渲染进程和主进程的 JavaScript 上下文 |
| `sandbox` | `true`（建议） | 沙箱模式，进一步限制渲染进程 |
| `webSecurity` | `true`（默认） | 不要设为 false |

#### ② Preload 脚本（`src/main/preload.ts`）

检查是否：
- 使用了 `contextBridge.exposeInMainWorld`（安全 ✅）而非直接挂载
- 暴露的 API 数量是否最小化（只暴露必要的，不暴露 `ipcRenderer.send` 原始方法）
- 没有暴露 `ipcRenderer.on` 给渲染进程

#### ③ 导航安全（`src/main/index.ts`）

检查：
- `loadURL` 是否只加载可信任的 URL（开发模式 `localhost:5173` 可接受，但不要加载任意 URL）
- 是否禁止了导航到外部链接

#### ④ 开发模式检查

开发模式下 `webContents.openDevTools()` 在生产构建中是否被禁用。

## 检查类别五：路径遍历与文件操作

### 检查什么

检查所有文件读写操作，看文件路径是否来自用户输入。

### 本项目关键检查点

#### CSV 导出（`ipc-handlers.ts:103`）
```typescript
writeFileSync(result.filePath, ...)
```
- `result.filePath` 来自 `dialog.showSaveDialog()` → 用户通过原生对话框选择路径 ✅
- 路径是用户自己选的，不存在路径遍历风险

#### CSV 导入（`ipc-handlers.ts:126`）
```typescript
readFileSync(filePath, 'utf-8')
```
- `filePath` 来自 `dialog.showOpenDialog()` → 用户通过原生对话框选择 ✅
- 路径是用户自己选的

### 判定标准

| 情况 | 评级 | 说明 |
|------|------|------|
| 文件路径全部来自原生对话框 | 🟢 安全 | 用户自己选的文件 |
| 文件路径来自前端用户输入（如输入框） | 🔴 危险 | 攻击者可能输入 `../../etc/passwd` |
| 文件路径有校验/白名单 | 🟢 安全 | 即使来自用户输入也做了防御 |

## 检查类别六：其他安全隐患

### ① 错误信息泄露

检查 IPC 处理函数中的错误处理，是否向渲染进程暴露了过多信息：

```typescript
// ⚠️ 警告：错误信息直接暴露给前端
catch (err: any) {
  return { success: false, message: `导出失败：${err.message}` }
}
```

**风险**：`err.message` 可能包含文件系统路径、数据库结构等敏感信息。

**建议**：生产环境中返回通用错误信息，详细错误只记录到日志。

### ② 危险操作缺少确认

检查 `clearAllExpenses`（清空所有数据）这种不可逆操作：
- 前端是否有确认对话框？→ 需要检查前端代码
- 主进程层面是否也应该有二次校验？

### ③ npm 依赖安全

```bash
npm audit
```

检查是否有已知漏洞的依赖包。

### ④ console.log 遗留

检查是否有调试时留下的 `console.log` 泄露敏感数据：
```bash
grep -rn "console\.\(log\|warn\|error\)" src/ --include="*.ts"
```

### ⑤ 数据未加密

SQLite 数据库文件中的数据是否明文存储？对于记账应用，这通常是可以接受的，但需要明确告知用户。

## 重要补充

### 什么是安全问题？

用生活类比解释：

| 类比 | 安全问题 |
|------|---------|
| 你家钥匙放在门垫下面 | **硬编码密码**：密码写在代码里，谁都能看到 |
| 快递员能打开你家所有柜子 | **权限过大**：每个功能都能访问全部数据 |
| 别人在你家门口偷听 | **敏感信息未加密**：网络传输/文件中数据明文可见 |
| 你家墙是纸糊的 | **容器安全配置弱**：攻击者很容易突破 |

### 修复优先级

- 🔴 **立即修复**：可以在当前版本就造成实际损害的
- 🟡 **尽快修复**：在特定条件下可能被利用的
- 🟢 **可以接受**：对当前应用场景风险极低的

### 本项目的安全边界

这款应用是**本地离线桌面应用**，安全威胁模型不同于 Web 应用：
- 没有网络攻击面（无服务器、无 API）
- 风险主要来自：本地恶意软件、物理访问、代码漏洞导致数据丢失
- 最重要的资产是用户的**记账数据（SQLite 文件）**
